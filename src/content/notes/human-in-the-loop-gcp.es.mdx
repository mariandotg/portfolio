Estoy construyendo un SaaS que todos los días busca ofertas de trabajo, las filtra y las matchea contra el perfil de cada usuario con un LLM. Hoy el flujo corre de punta a punta sin nadie en el medio. En la versión siguiente, eso cambia: el flujo se pausa hasta que el usuario elige a qué ofertas aplicar, y recién ahí genera un CV adaptado para cada una.

El usuario puede tardar diez minutos, dos días o no contestar nunca. Ese hueco es el tema de esta nota.

Lo diseñé en dos tracks: uno oficial, que va a producción, y uno experimental, donde pruebo GCP completo. Armar los dos me obligó a comparar tres formas de resolver la misma pausa.

<Callout type="note" title="La tesis">
Esperar a un humano no es un problema de cómputo. Es un problema de **estado**. Las tres opciones guardan ese estado en lugares distintos: el motor de Workflows, la base de metadatos de Airflow o tu propia base de datos. Los trade-offs salen de ahí.
</Callout>

## El problema: un flujo que espera días un click

Si dejo la espera en memoria de un proceso de Cloud Run, falla por tres razones.

- **Timeouts.** Un request de Cloud Run tiene un timeout máximo. Un job tiene otro. Ninguno de los dos está pensado para esperar 48 horas a un humano.
- **Costo.** Un contenedor que espera con la CPU asignada se cobra mientras espera. Pagás cómputo por no hacer nada.
- **Estado perdido.** Si la instancia se reinicia, por un deploy o por un escalado, la espera en memoria desaparece. No hay forma de saber qué corridas estaban esperando ni desde cuándo.

> TODO(verificar): timeout máximo actual de un request de Cloud Run (servicios) y de una tarea de Cloud Run Jobs, para citar las cifras con link en vez de describirlas.

Lo que necesito no es un proceso que espere. Necesito un lugar donde quede escrito "la corrida 42 espera la decisión del usuario 7 desde el martes a las 9", y algo que reaccione cuando llegue esa decisión o cuando venza el plazo.

## Opción A: Cloud Workflows con callbacks

Si el proceso puede desaparecer, la espera tiene que persistir fuera de él. Cloud Workflows hace exactamente eso: definís pasos en YAML, y el motor guarda el estado de cada ejecución entre paso y paso. Para esperar a un humano tiene una primitiva directa, los callbacks.

El flujo tiene tres partes. `events.create_callback_endpoint` crea una URL única para esa ejecución. Un paso le manda esa URL a mi servicio de notificaciones, que le avisa al usuario. Después, `events.await_callback` suspende la ejecución hasta que alguien haga un POST a esa URL o venza el timeout.

```yaml
- create_callback:
    call: events.create_callback_endpoint
    args:
      http_callback_method: "POST"
    result: callback
- notify_user:
    call: http.post
    args:
      url: https://notifier-xxxx.run.app/approval-requests
      auth:
        type: OIDC
      body:
        run_id: ${run.id}
        callback_url: ${callback.url}
```

La espera y la ramificación quedan así:

```yaml
- await_approval:
    try:
      call: events.await_callback
      args:
        callback: ${callback}
        timeout: 172800 # 48 h, en segundos
      result: approval
    except:
      as: e
      steps:
        - on_timeout:
            switch:
              - condition: ${"TimeoutError" in e.tags}
                return: "expired"
        - rethrow:
            raise: ${e}
- route:
    switch:
      - condition: ${approval.http_request.body.decision == "approved"}
        next: tailor_cvs
    next: mark_rejected
```

> TODO(verificar): que el body JSON del callback llegue parseado en `approval.http_request.body`, que el tag del error de timeout sea exactamente `TimeoutError` y cuál es el timeout máximo que acepta `events.await_callback`.

La web no llama al callback desde el navegador. La URL exige un token de IAM: el que hace el POST necesita el permiso `workflows.callbacks.send` sobre el workflow. En mi caso, el backend de la API valida que el usuario sea dueño de la corrida y después hace el POST con su service account:

```bash
curl -X POST "$CALLBACK_URL" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -d '{"decision": "approved", "offer_ids": ["o-81", "o-112"]}'
```

> TODO(verificar): qué rol predefinido mínimo incluye `workflows.callbacks.send` (creo que `roles/workflows.invoker`).

Lo que me gusta de esta opción es que el código se lee como el proceso. No hay polling, no hay tabla de estados, no hay job de vencimientos. El timeout es un argumento.

El costo de la espera también es casi nulo. Según los [precios de Workflows](https://cloud.google.com/workflows/pricing), los pasos internos cuestan 0,01 USD cada 1.000 (5.000 gratis por mes) y los externos 0,025 USD cada 1.000 (2.000 gratis por mes). **Esperar un callback cuenta como un paso externo, sin importar cuánto dure la espera.** Cada reintento cuenta como un paso más.

Hice la cuenta para 1.000 usuarios con una corrida diaria y 1 callback por corrida. Los supuestos: un mes de 30 días, unos 15 pasos internos por corrida (es un supuesto de diseño, no una medición) y la franquicia gratis completa disponible.

- 30.000 ejecuciones por mes × 15 = 450.000 pasos internos. Menos 5.000 gratis: 4,45 USD.
- 30.000 callbacks. Menos 2.000 gratis: 0,70 USD.
- Total: 5,15 USD por mes. Cubre solo Workflows, no Cloud Run, ni el LLM, ni el almacenamiento.

> TODO(verificar): si las llamadas HTTP a servicios propios en Cloud Run (`*.run.app`) cuentan como pasos internos o externos. Si son externos, el `http.post` de notificación suma 30.000 pasos externos más y el total sube a 5,90 USD por mes.

El límite que importa no es el precio. Las [cuotas de Workflows](https://docs.cloud.google.com/workflows/quotas) fijan 10.000 ejecuciones activas por región y proyecto, con 100.000 más en backlog. Una ejecución que espera un callback está activa. Con 10.000 usuarios que todavía no contestaron, la ejecución 10.001 no arranca: va al backlog hasta que alguien apruebe o venza. La duración máxima de una ejecución es de 1 año, así que el plazo de 48 horas no es un problema. La memoria para variables es de 512 KB por ejecución, así que la lista de ofertas matcheadas tiene que viajar como IDs, no como documentos completos.

> TODO(verificar): si el límite de 10.000 ejecuciones activas se puede ampliar por solicitud de cuota, y si el backlog es automático o hay que habilitarlo.

## Opción B: Airflow (Composer) con sensors

Workflows guarda la espera, pero cada aprobación pendiente ocupa un cupo de ejecuciones activas. Airflow resuelve la capacidad distinto. Su herramienta para esperar es un sensor: una tarea que pregunta "¿ya pasó?" hasta que la respuesta es sí o vence su timeout. La decisión del usuario queda en la base de la aplicación, y el sensor la consulta.

El detalle crítico es el modo. En `mode="poke"`, el sensor ocupa un worker slot durante toda la espera: duerme entre consultas, pero no suelta el slot. Para una espera de segundos da igual. Para una espera de 48 horas, cada usuario que no contestó es un slot bloqueado sin hacer nada. Con cien aprobaciones pendientes ocupás cien slots, si el entorno tiene tantos, según la [doc de sensors](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/sensors.html).

En `mode="reschedule"`, el sensor consulta, y si la respuesta es no, libera el slot y le pide al scheduler que lo vuelva a correr más tarde. Entre consulta y consulta, la espera vive en la base de metadatos de Airflow, no en un proceso.

```python
from airflow.decorators import task
from airflow.providers.postgres.hooks.postgres import PostgresHook
from airflow.sensors.base import PokeReturnValue

@task.sensor(mode="reschedule", poke_interval=600, timeout=48 * 3600)
def wait_for_approval(run_id: str) -> PokeReturnValue:
    row = PostgresHook("app_db").get_first(
        "SELECT decision FROM approvals WHERE run_id = %s", parameters=(run_id,)
    )
    decision = row[0] if row else None
    return PokeReturnValue(is_done=decision is not None, xcom_value=decision)

@task.branch
def route(decision: str) -> str:
    return "tailor_cvs" if decision == "approved" else "mark_rejected"
```

Cuando vence el timeout, el sensor falla con `AirflowSensorTimeout`. Si preferís tratar el vencimiento como un camino normal, `soft_fail=True` marca la tarea como skipped, pero entonces tenés que cuidar las trigger rules de las tareas siguientes.

La alternativa moderna son los **deferrable operators**. La tarea se suspende y le entrega la espera a un trigger asíncrono que corre en un componente aparte, el triggerer. El triggerer maneja muchas esperas en un solo proceso con `asyncio`, y la tarea vuelve a un worker solo cuando el trigger dispara. Es más eficiente que reschedule para miles de esperas, pero para consultar mi base necesito escribir un trigger propio.

> TODO(verificar): si `SqlSensor` del provider `common.sql` ya soporta `deferrable=True`, o si hace falta un trigger custom.

Además del sensor, tengo que modelar cuántos DAG runs quedan activos. Si cada corrida de usuario es un DAG run, tengo miles de DAG runs activos esperando a la vez. Airflow limita los DAG runs activos por DAG con `max_active_runs_per_dag`, que por defecto es bajo. Hay que subirlo, y el scheduler tiene que procesar todas esas tareas reprogramadas.

> TODO(medir): cuánta carga agrega al scheduler y a la base de metadatos tener 1.000 sensors en reschedule con `poke_interval=600`. Medirlo en el entorno small de Composer con un DAG sintético: latencia de scheduling y CPU del scheduler durante 24 h.

El costo es lo que más pesa. Composer, renombrado [Managed Service for Apache Airflow](https://cloud.google.com/products/managed-service-for-apache-airflow/pricing), cobra 0,06 USD por DCU-hora en us-central1, y cobra mientras el entorno existe, haga algo o no. Una [estimación de la comunidad](https://discuss.google.dev/t/cloud-composer-3-pricing-explanation/158381), no oficial, calcula unos 12 DCU para un entorno small en reposo: unos 17 USD por día, unos 500 USD por mes. Eso es antes de correr una sola tarea.

Hay una concesión que importa. Si Composer ya sostiene mi catálogo, lo que cuenta es el costo adicional de las aprobaciones, no todo el entorno. Ese costo adicional es la carga extra sobre el scheduler, y todavía no la medí.

## Opción C: una máquina de estados con eventos

Para no pagar un entorno permanente y administrar mis propias esperas, puse el estado en `runs`. Cada corrida es una fila, y su `status` recorre una máquina de estados: `matched → waiting_approval → tailoring → done`, con dos salidas laterales, `rejected` y `expired`. Ningún proceso espera. Cuando el matcher termina, deja la corrida en `waiting_approval` con un `expires_at` a 48 horas y le avisa al usuario. Después, nada corre hasta que pase algo.

Pueden pasar dos cosas. El usuario aprueba: la API hace un `UPDATE` y publica un mensaje en Pub/Sub, que despierta al servicio de Cloud Run que genera los CVs. O no contesta: un job horario de Cloud Scheduler marca como `expired` las corridas vencidas.

Las dos cosas pueden pasar casi al mismo tiempo. También puede pasar que el usuario apriete "aprobar" dos veces. Por eso la transición es condicional:

```sql
-- API: el usuario aprueba
UPDATE runs
SET status = 'tailoring',
    approved_offer_ids = $2,
    updated_at = now()
WHERE id = $1
  AND status = 'waiting_approval'
  AND expires_at > now()
RETURNING id;

-- Job horario: vencimientos
UPDATE runs
SET status = 'expired', updated_at = now()
WHERE status = 'waiting_approval'
  AND expires_at <= now()
RETURNING id;

-- Consumidor: reclama la corrida (15 min es un valor ilustrativo)
UPDATE runs
SET claimed_until = now() + interval '15 minutes'
WHERE id = $1 AND status = 'tailoring'
  AND (claimed_until IS NULL OR claimed_until < now())
RETURNING id;
```

El `UPDATE` toma un lock de fila. En READ COMMITTED, el segundo `UPDATE` espera, y cuando el primero commitea reevalúa el `WHERE` sobre la versión ya actualizada, así que no encuentra la fila ([doc de aislamiento de Postgres](https://www.postgresql.org/docs/current/transaction-iso.html)). Solo un actor avanza la corrida. Si el `RETURNING` vuelve vacío, la API no publica nada y le responde al usuario que la corrida ya no acepta cambios.

Esto no termina ahí. Pub/Sub entrega **at-least-once**: el mismo mensaje puede llegar dos veces, y dos workers pueden recibirlo a la vez. Un upsert por `(run_id, offer_id)` evita filas duplicadas, pero no evita dos generaciones concurrentes de los mismos CVs. Por eso el consumidor reclama la corrida con un lease antes de generar, con el tercer `UPDATE` del snippet. Si no devuelve fila, otro worker la tiene: hace ack y descarta el mensaje.

Cuando el worker termina, hace el upsert de cada CV por `(run_id, offer_id)` y cierra con `UPDATE runs SET status = 'done' WHERE id = $1 AND status = 'tailoring'`. Si el worker muere, el lease vence solo. El lease distingue trabajo abandonado de trabajo activo. Los 15 minutos son ilustrativos, no medidos.

> TODO(medir): duración del lease y umbral del barrido — p95 de generación de CVs por corrida, medido con timestamps en el consumidor.

Queda un hueco que tengo que nombrar: el `UPDATE` de aprobación y el `publish` no son atómicos. Si la API commitea y se cae antes de publicar, la corrida queda en `tailoring` sin nadie que la procese. Lo resuelvo con el job horario: también republica las corridas en `tailoring` con lease vencido o nulo y `updated_at` viejo. Como el consumidor reclama antes de generar, republicar es seguro. La versión prolija sería un outbox transaccional, pero el barrido alcanza mientras el volumen sea bajo.

## La comparación

| | A: Workflows + callbacks | B: Composer + sensors | C: tabla de estados + eventos |
|---|---|---|---|
| Dónde persiste la espera | La ejecución en el motor de Workflows | Metadatos de Airflow (estado del sensor) y la decisión en la base de la app | La fila en `runs` |
| Costo de la espera | 1 paso externo por espera, sin importar la duración | Una consulta por `poke_interval`, pagada dentro del entorno | Marginal: una fila. Del sistema: el barrido horario despierta Neon |
| Costo en reposo | Cero | Unos 500 USD/mes (estimación de la comunidad) | Cero o casi cero |
| Duración máxima | 1 año por ejecución | Sin límite práctico; la define el `timeout` del sensor | Sin límite; la define `expires_at` |
| Visibilidad | Consola de Workflows: cada ejecución, su paso actual y sus variables | UI de Airflow: grid, logs y estado de cada tarea | La que construyas: un `SELECT status, count(*)` o un dashboard |
| Testing local | Limitado: no tengo un emulador del motor | Docker con Airflow local, sin Composer | Postgres local y tests comunes |
| Operación | Casi nula | Un entorno para mantener, actualizar y pagar | Un job horario y la disciplina de la máquina de estados |
| Lock-in | Alto: YAML de Workflows | Bajo: Airflow es open source | Bajo: SQL y una cola |
| 10.000 usuarios esperando | En el límite de 10.000 ejecuciones activas por región y proyecto | 10.000 tareas reprogramadas para el scheduler y DAG runs activos que configurar | 10.000 filas en una tabla |

> TODO(verificar): si existe un emulador oficial o local de Cloud Workflows. No conozco uno, pero no quiero afirmarlo sin confirmarlo.

La espera persiste en los tres casos. Cambia quién administra su capacidad y quién paga su operación.

Esta comparación tiene límites. No mide latencia ni costo real: los costos son de lista y faltan mediciones propias. Tampoco cubre otras opciones del mismo problema, como Cloud Tasks con un ETA o un servicio de workflows durables fuera de GCP.

## Cuál elegí y por qué

**En producción, C.** El track oficial corre con Cloud Scheduler, Pub/Sub, Cloud Run y Postgres en Neon, y el estado de cada corrida vive en `runs`. No lo elijo por costo: contra A, el ahorro es de unos 5 USD por mes. Lo elijo por tres razones. Testeo todo con Postgres local. Controlo el estado de punta a punta. Y no me ato a ningún proveedor. De yapa, la tabla cuesta cero o casi cero en reposo.

Ese control se paga con trabajo propio. Escribo yo los vencimientos, la transición atómica, la idempotencia y la visibilidad. Un orquestador me daría las cuatro cosas hechas.

**En el track experimental, A.** Acá uso GCP completo: Composer para el pipeline batch del catálogo y Workflows para la corrida de cada usuario, aprobación incluida. Workflows es la solución más limpia de las tres. El YAML describe el proceso tal como lo explicaría en una pizarra, y la espera cuesta un paso. Si el límite de 10.000 ejecuciones activas fuera un problema real, ya tendría un negocio que paga la solución.

**B, solo porque ya existe.** No pondría Composer para esperar aprobaciones. Lo uso para el pipeline batch del catálogo: scraping, normalización y deduplicación de ofertas. Es trabajo de datos, con dependencias entre tareas, backfills y reintentos por partición, y ahí Airflow se gana su costo. Si un día el entorno ya existe y la aprobación es una tarea más de un DAG de datos, un sensor deferrable es razonable. Para una corrida por usuario, no.

## Un orquestador mínimo

Una tabla de estados con eventos es un orquestador mínimo que controlás vos. No tiene consola ni features. Pero sé dónde está cada corrida, porque es una fila que puedo consultar.

<Callout type="rule" title="La regla">
**Workflows orquesta servicios; Composer orquesta datos.** Si el problema es "llamá a este servicio, esperá, ramificá según la respuesta", Workflows. Si es "procesá esta partición después de aquella", Airflow.
</Callout>
